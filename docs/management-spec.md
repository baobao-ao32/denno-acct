# 会計管理部分 仕様（2026-11-24 Aoba回答の反映）

生成器（ローカルPython）は現状の試作でよい。次は会計管理部分（HTMLフォーム + 会計管理ページ）を作る。

## 1. 生成器の手順（確定イメージ）
1. サークルのGoogleドライブから当年度の「領収書」フォルダをzip等でDL
2. 会計記録とフォルダ内分類が一致しているか確認（取引の代表カテゴリ vs 保存先フォルダ。不一致はリストで出す）
3. PDF領収書は画像に変換
4. 領収証等一覧テンプレに領収書を差し込み、収支報告書テンプレにデータを差し込む

## 2. Googleドライブ構成（確定）
```
会計/
  2025年度/
    2025年度会計記録   （スプレッドシート）
    領収書/
      運営費/
      制作練習費/
      参加出展費/
  2026年度/
    ...
```
- 領収書フォルダの分類名は報告書の大分類名（運営費/制作練習費/参加出展費）に合わせる。人間がDriveを直接見ても報告書と対応が取れるため
- どのフォルダに入るかは取引の「代表カテゴリ」（金額最大の明細のカテゴリ）で決める（v1のルールを踏襲）

## 3. 年度スプレッドシートのタブ構成
Aoba指定の3タブ（サマリ/収入/支出）は「報告書のための集計ビュー」。その土台として取引明細タブが要る。

| タブ | 種別 | 内容 |
|---|---|---|
| 取引明細 | 入力データ（GASが追記） | 取引×明細を行として保持。ID列（種別/カテゴリ/科目/支払方法）+ 表示名列 + 領収書参照 + 証明不可フラグ + voidフラグ |
| サマリ | 自動集計 | 収入合計 / 支出合計 / 差引収支 / 領収証等による支出の証明ができない額 / 直接経費額 |
| 収入 | 自動集計 | 列: 科目 / 金額 / 前年度比較増減 / 備考。科目はマスタ通り（分配金・役員報酬・会費収入・頒布売上・その他） |
| 支出 | 自動集計 | 列: 大分類 / 科目 / 金額 / 備考。（大分類, 科目）で集計し、大分類の固定順で並べる |
| 設定 | 手入力（年次メタ） | 団体名（電脳サークル・固定）/ 会計氏名・学科 / 代表氏名・学科 / 前年度繰越金 / 前年度科目別実績（初年度のみ） |

- 集計は登録のたびにGASが再計算して書き込む（数式ではなく値）。生成器（層1JSON）と集計タブが同じ結果を共有できる
- 前年度比較増減は、前年度フォルダのスプレッドシートの収入タブ（または設定の前年度実績）から引く

### 繰越金の扱い（決定: 報告しないが、スプシで確認できるようにする）
- 収入タブに「前年度繰越金」の行を置くが、**報告対象外フラグ**を付け、収支報告書の収入の部には出さない
- サマリでは独立項目として表示する: 前年度繰越金 / 収入合計（繰越金を含まない、報告書と一致）/ 年度末残高（= 繰越金 + 差引収支）
- 金額は設定タブで年次に1回入力する（取引としては登録しない）

## 4. 確定した回答（2026-11-24）
1. 繰越金: 報告しない前提。ただしスプシからは確認できるようにする → 上記 §3 の方式
2. 支出の報告科目: **マスタ選択式**で確定
3. 団体名: **「電脳サークル」**（正式登録名として確定。生成器の仮置きがそのまま正解だった）
4. 領収書が無い支出: 発生しない見込みだが、**証明不可フラグは実装する**

## 4.5 支出明細のカラム（2026-11-24 Aoba指定）
取引明細タブの支出行が持つカラム。基本はv1の支出明細の項目を踏襲し、報告科目を追加したもの。
集計タブ「支出」（大分類/科目/金額/備考）は、この明細から自動集計される。

| # | カラム | 入力 | 内容 |
|---|---|---|---|
| 1 | 精算状態 | 会計係が更新 | 購入者へ返金したか。値: 未精算 / 精算済み / 精算不要（部費から直接の場合） |
| 2 | 会計担当メモ | 会計係が記入 | 自由記述 |
| 3 | 購入日 | 購入者 | |
| 4 | 購入者氏名 | 購入者 | |
| 5 | 用途別金額合計 | 購入者 | この明細行の金額 |
| 6 | 用途名 | 購入者 | 自由記述（例: 学園祭参加のため） |
| 7 | 用途別カテゴリ名 | 購入者（選択） | 大分類3種のどれか（運営費/制作練習費/参加出展費）。裏ではカテゴリIDで保持 |
| 8 | 用途別品目名 | 購入者 | 自由記述（例: 学園祭参加費） |
| 9 | 報告科目 | 購入者（マスタ選択） | 報告書の科目（例: 参加費登録料）。**新規追加**。集計はこの単位でまとめる |
| 10 | 用途別メモ | 購入者 | 自由記述 |
| 11 | 購入先 | 購入者 | |
| 12 | 支払方法 | 購入者（選択） | 部費から直接 / 個人で立て替え のいずれか（IDで保持） |
| 13 | 領収書全体の金額 | 購入者 | 取引（領収書）単位の総額。明細行ごとに同じ値が入る（v1踏襲） |
| 14 | 領収書URL | 自動 | 保存した領収書のURL |
| 15 | 領収書保存先のパス | 自動 | Drive内の保存パス |
| 16 | 領収書保存カテゴリ | 自動 | 代表カテゴリ（金額最大の明細のカテゴリ）のフォルダ名 |
| 17 | 報告年月日時間 | 自動 | 購入者が報告（送信）した日時 |
| 18 | 記録実行時刻 | 自動 | システムが台帳へ記録した日時 |

例（Aoba提示）: 用途=学園祭参加のため / カテゴリ名=運営費 / 品目名=学園祭参加費 / 科目=参加費登録料
→ 集計では（運営費, 参加費登録料）の行に金額が積まれる。

注: v1にあった「チェック済み」列は今回の指定に含まれていないため落とす（精算状態と会計担当メモで代替できる）。
システム内部用に申請ID/明細ID/voidフラグ/証明不可フラグも別途持つが、上記は人間が見るベース項目の一覧。

### 収入の「その他」の扱い（2026-11-24 Aoba指定）
- 収入明細に「内容（詳細）」欄を持ち、科目=その他収入 の場合は具体的に何の収入かを必須記録とする
- 内容は取引明細に残し、収入タブの備考の下書き候補として生成器に渡せるようにする

## 5. フォーム / 管理ページ（実装対象）
- 入力フォーム（試作 form.html を土台）: 取引登録。明細に報告科目の選択を追加。領収書なし支出は証明不可フラグ + 理由で登録可能にする（現試作の「領収書必須で送信停止」は緩和）
- 会計管理ページ: 年度切替、取引一覧（void操作）、集計タブと同じサマリ表示、領収書フォルダとの分類一致チェック結果の表示
- 経路は決定済み: ブラウザ → Cloudflare Worker（トークン保持）→ GAS API → Drive/Sheets

### 5.1 提出フォームの構成（2026-11-24 確定）
収入報告: 1回の提出につき1項目のみ。
- 収入の種類（科目マスタから選択、ID保持）
- 金額
- 詳細欄（種類=その他収入 の場合に表示し必須にする）
- 日付欄は置かない。年度帰属は報告日（送信時に自動記録される報告年月日時間）で判定する（§5.2）。分配金は年度始まりに受け取る規定のため、この運用で問題ない（2026-11-24 Aoba判断）

支出報告: まず領収書をアップロードさせる。1回の提出で最大5件まで。
- 対応形式: jpeg / png / webp / PDF。HEICは受け付けてブラウザ側でJPEGに変換してからアップロードする（原本は撮影者の端末に残る前提）
- 冒頭に「領収書あり／なし」の分岐を置く。なしの場合はアップロードを飛ばし、証明不可フラグ + 理由（必須）の経路にする
各領収書ごとに聞く内容:
- 購入日 / 購入者氏名 / 購入先 / 支払方法（部費から直接・個人で立て替え、ID保持） / 領収書全体の金額
- 用途は「+」ボタンで追加できる形で、用途ごとに: 用途名 / 用途別カテゴリ名（大分類3種、ID保持）/ 用途別品目名 / 報告科目（マスタ選択）/ 用途別メモ / 用途別金額合計
- 用途は1領収書あたり最大10件。それ以上は提出を分ける
- 検証: 用途別金額合計の総和 = 領収書全体の金額 をフォーム側でリアルタイム照合し、一致しないと送信不可

#### 分割提出された同一領収書の扱い（2026-11-24 追加設計）
用途10件超で提出を分けると、同じ領収書ファイルが複数回アップロードされ、複数フォルダに散らばる恐れがある（Aobaの懸念）。対策:
- アップロード時にファイルのハッシュ（SHA-256）を計算し、同年度内で既存の領収書と一致したら「登録済みの領収書です。用途を追加しますか？」と提示し、ファイルを複製せず既存の取引へ用途だけを追記する
- 保存フォルダは取引全体の代表カテゴリで決める。用途の追記で代表カテゴリが変わったら、GASがファイルを正しいフォルダへ移動する
- 報告書生成時も取引単位で1枚として扱うので、重複掲載は起きない

#### 複数カテゴリに跨る領収書の帰属（確定）
- 保存フォルダ（代表カテゴリ）と領収証等一覧での掲載先は、同一ルールで決める
- ルールは **金額割合が最大** のカテゴリ／科目（公式ガイド「支出割合が最大の科目」と一致。2026-11-24 Aoba確認済み — 「数の多い」は金額割合の意図だった）

### 5.2 年度帰属ルール（2026-11-24 確定）
- 年度は **4月スタート**（例: 2026年度 = 2026-04-01 〜 2027-03-31）
- 収入: **報告日**（フォーム送信日 = 報告年月日時間）を基準に年度を決める
- 支出: **購入日** を基準に年度を決める

## 5.5 年度スプレッドシートの作り方（推奨案、2026-11-24）
**テンプレコピー方式 + コードによる検証** を推奨する。

- 理由: このスプシは人間が直接読んで触る帳簿。完全自動生成にすると、列幅・金額書式・固定行・プルダウン等の「見た目と使い勝手」を全てGASコードで再現することになり、調整のたびにコード変更＋再デプロイが要る。テンプレならSheetsの画面で直して終わる（後任への引き継ぎにも有利）
- テンプレに持たせるもの: 5タブの骨格、ヘッダ、列幅、書式、入力規則（精算状態等のプルダウン）、集計タブのレイアウトとラベル
- コード側に持たせるもの: 期待するタブ名とヘッダの定義（検証用）。年度作成時にテンプレをコピー → 年度フォルダへ配置・リネーム → 設定タブへ年度等を書き込み → ヘッダを検証してから運用開始。テンプレが壊れていたら年度開始時点で検出できる
- 集計タブの中身は値で書き込む方式なので、テンプレ側に数式は不要
- テンプレの置き場所: 「会計」ルート直下に「テンプレート_会計記録」として1つだけ置き、ファイルIDをGAS側の設定に持つ。誤編集・誤削除が怖ければ閲覧のみ共有にして編集者を絞る

## 6. ソースコードの管理場所
- **推奨: GitHub に新規 private リポジトリ（例: denno-acct）を作り、そこでgit管理する**
  - Googleドライブにgitリポジトリを置くのは避けたい。同期型ドライブは .git 内部ファイルを書き換え・競合させやすく、履歴破損の原因になる。コードの閲覧性もGitHubが圧倒的に良い
  - ドライブは「データ置き場」（スプレッドシート・領収書）として既に役割が決まっている。コードまで混ぜると引き継ぎ時に混乱する
  - 容量は無関係（ソースは数MB以下）。5TBは領収書やバックアップに使う方が活きる
  - どうしてもドライブにも置きたい場合は、GitHubを正として、節目ごとにソース一式のzipをドライブへアーカイブする形なら両立できる
